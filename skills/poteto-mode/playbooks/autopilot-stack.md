### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default and the only forge tooling installed here: use `gh pr ...` for PR create, edit, view, watch, and merge operations. Origin is **not installed**, so no step may depend on `origin pr ...`, and Graphite (`gt`) is never required. One owner subagent per PR, isolated in its own git worktree off its own branch, owns its change end to end: build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (the local `deslop` skill), the `no-comments` skill, and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained, and concurrent owners must never share one mutable write target: every owner holds its own worktree and branch, while reviewers and verifier lanes stay read-only against a reported head SHA or a copied-out artifact and never write into an author's worktree (principle-separate-before-serializing-shared-state). Worktree creation and removal stay idempotent. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on the wake chain.** The root runs an audit tick roughly once an hour. Cursor's `/loop` does not exist here, so arm each tick as a bounded local poll: one cycle per one-hour interval, counting against the tick budget set in step 3, with one status line per tick. Never leave the cadence to memory or lossy completion notifications, and never chain ticks into an unbounded overnight run. At each tick, re-read this playbook from trunk with `git show origin/main:pstack/skills/poteto-mode/playbooks/autopilot-stack.md`, then re-read `goal.md`. Audit the operation against both. Fix drift during that tick. Probe each owner with a generic liveness or status check through the `subagent` tool's handles. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Probe all subagents and end the tick per Autopilot-full step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's explicit go, write the program's objective, the done condition, and the run budget into `orchestrate/<project-slug>/goal.md`; there is no `/goal` command here, and that file is what carries the objective across turns until the chain is done. Set the budget now: a maximum wall-clock duration and a maximum tick count, defaulting to 8 hours or 8 ticks, so the tick budget and the wall-clock ceiling bite at the same moment, after which the program reports and stops. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `gh pr create --base <parent-branch>`. Retarget an existing PR with `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice in its own worktree and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in GitHub, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, the budget used against the cap, and anything parked or excluded with the reason.
