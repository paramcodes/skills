### Autonomous run

**You own the exit condition. Define done, then drive to it without stopping.**

There is no Cursor `/loop` on this machine. The wake mechanism here is a bounded poll you drive yourself, and it is always finite: a fixed iteration budget, a wall-clock deadline, or both, chosen before the first iteration.

1. State the exit condition as a checkable predicate before the first iteration (tests green, repro fixed, all N PRs merged, pixel-diff zero).
2. Pick the bounded wake mechanism. Cursor's `/loop` is gone; the local equivalents are a short foreground poll between iterations, or a background/async subagent that sleeps on a monitored shell and returns. No event to watch means a fixed interval sized to when the result is worth re-checking. Whatever you pick, set the budget now: a maximum iteration count **and** a maximum wall-clock duration (default: 20 iterations or 2 hours, whichever comes first). An event to watch (CI, a merge, a ref advancing) gets a watcher subagent that wakes you on the event, with a long time-based heartbeat as fallback. State the budget in the first progress line so a cold-start reader sees it. There is no hidden infinite loop: when the budget is spent, the run stops and reports, it does not roll over into a new session.
3. Each iteration makes the smallest change the evidence justifies, verifies it against the predicate, commits if it advanced, discards changes that didn't help. Belt-and-suspenders that "might help" gets reverted, not left to ride.
   Sequence the work via the **sequence-verifiable-units** principle skill, verifying each unit before the next instead of batching checks at the end.
4. Mid-run discoveries are yours. Address broken skills, related bugs, flaky verifiers, review noise, tooling failures, orphaned follow-ups, and fixable drift yourself via poteto-mode. Put out-of-band fixes in their own PR. Do not park reversible work for the human or use the harness's structured question tool. Surface only irreversible actions, genuine product or preference calls no experiment can settle, or a real dead end. Keep the predicate as the main drive, and return to it after each side fix. No merge, deploy, billing change, or destructive action without explicit user authorization, however far the budget stretches.
5. Checkpoint every iteration via the **show-me-your-work** skill, a row for what changed and whether the predicate moved. Emit one short progress line per iteration, so a reader stepping away can see where the run stands without reading the trail.
6. Stop when the predicate is met. A plateau is not a stop, so keep going and pivot your approach to push past it — but only inside the budget. Surface a genuine dead end rather than spinning, and never relax the predicate to declare victory. When the budget is exhausted before the predicate holds, stop anyway, write the resume note per `playbooks/pause-safely.md` with the exact command to continue, and report the run as incomplete rather than done.

**Reply:** the exit condition, the budget and where it landed (iterations used of the maximum, elapsed against the deadline), what landed, what was discarded, final predicate state, and the resume note path if the run stopped on budget rather than on done.
